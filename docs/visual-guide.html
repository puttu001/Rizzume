What the system is

A resume-aware interview practice app. Spoken answers become editable text before the interview engine evaluates them.

Voice architecture

A cascaded pipeline: speech-to-text → text reasoning → text-to-speech. Audio input is one upload per answer.

Important scope boundary

Not a streaming voice agent. There is no WebRTC/WebSocket media session, VAD, partial transcript stream, or barge-in loop.

Why audio bytes go to Blob

The queue carries a small blob name rather than large audio bytes. The worker downloads the file when it processes the job.

Why there are two response styles

STT is a background task with job status polling. Short question TTS returns MP3 bytes inline so playback can begin as the next turn starts.

Service internals

Each service is independently packaged. Interview reasoning is an internal module of interview-service; conversation history is behind its own HTTP and database boundary.

API gateway

FastAPI route proxy → JWT middleware → shared async HTTP clients. Copies method, query, headers and body; injects X-User-Id.

services/api-gateway/app/{middleware,api,core,clients}

Auth service

Route → auth service → user repository → auth_db. bcrypt hashes passwords; signed JWTs carry subject, type and expiry.

services/auth-service/app/{api,services,repositories,utils}

Interview service

Route and ownership checks → orchestration → repositories, internal engine modules, Blob client, conversation HTTP client.

services/interview-service/app/{api,services,engine,clients}

Audio API + worker

API stores media and creates jobs; independent Celery worker fetches audio and calls STT. Speech endpoint calls TTS inline.

services/audio-service/app/{api,worker,providers,storage}

Conversation service

Append commits a numbered turn to Postgres and invalidates the Redis list cache. Reads use cache first, DB otherwise.

services/conversation-service/app/{api,services,repositories}

Report service scaffold

Not included in local Compose or the interview completion path. Current worker task is a ping; interview-service generates feedback itself.

services/report-service/app/worker/tasks.py

Interview engine: three calls at different moments

1. Planner

At creation: resume + role → bounded question count, greeting, opening question.

2. Next-step decision

After each answer: transcript + current state → ask/end, remark, question, next difficulty.

3. Feedback generator

At completion: full text transcript → score, strengths, improvement areas, summary.

All use gpt-5.4-mini with Pydantic structured output. Follow-up selection and difficulty adjustment are intentionally one model call.

Data ownership and state

Each domain service owns its database. The relationship IDs are logical references because the records live in separate databases.

auth_db

users

id UUID · email unique · hashed_password · created_at

Owner: auth-service

interview_db

interviews

id · user_id · role/status/difficulty · question counts · resume text/blob ref · feedback JSON · timestamps

Owner: interview-service

conversation_db

conversation_turns

interview_id · unique turn number per interview · question/answer role · text · timestamp

Owner: conversation-service

Redis · transcript cache

Key: session:{id}:turns. JSON list, two-hour TTL. Cache is invalidated after appends; Postgres remains the source of truth.

Redis · Celery broker/result

Audio queue is named audio_tasks. Job argument is the blob name; task status and transcript are read by job ID.

Azure Blob

Private object storage holds original resumes and uploaded audio. Services access objects by name. No cleanup lifecycle is shown in this code.

Interview state

in_progress creation saves opening question → each answer adds transcript and either advances count/difficulty or completes → completed saves feedback.

Browser turn state

idle → recording → transcribing → reviewing → submitting → idle. Completion returns feedback. Error returns to review or idle for retry.

Cross-service consistency: each transcript append commits independently. There is no shared SQL transaction or outbox spanning interview_db, conversation_db, Blob Storage, Redis, and OpenAI.

Voice AI concepts

Filter the glossary. “Built” means represented in this code path; “not built” marks common real-time voice features this app does not implement.

STT / ASR

Convert a recording into text. Here: gpt-4o-mini-transcribe in an audio worker.

Text reasoning

Use resume, role and transcript to select an interview action. Here: gpt-5.4-mini Responses API.

TTS

Convert interviewer text into speech. Here: gpt-4o-mini-tts, alloy voice, MP3.

Human correction

Candidate can edit recognized words before the engine sees the answer.

Interview talking points

Short, accurate answers you can use to explain the design, tradeoffs, and the next architecture step.

“Walk me through a spoken answer.”

“The browser records one full answer with MediaRecorder, uploads it through the gateway, and gets a Celery job ID. The audio service stores bytes in Blob and queues only the blob name. A worker calls STT and stores the transcript in Redis as the task result. The UI polls, lets the candidate edit the text, and submits it to interview-service. The interview engine selects the next question or completes with feedback; TTS returns the next prompt as MP3.”

“Is it a real-time voice agent?”

“No. It is a turn-based, cascaded pipeline. Recording ends on a user action; STT runs after upload; the response is generated after transcript submission. There is no continuous media transport or partial audio/transcript streaming.”

“Why queue transcription?”

“STT can take longer than a normal request. A job ID frees the API request quickly and lets a worker scale separately. The tradeoff is a broker, worker, polling delay, task-result lifecycle and uploaded-file cleanup.”

“Why separate services and databases?”

“Auth, interview orchestration, conversation history and audio processing have clear ownership and separate dependencies/workloads. Services exchange data over HTTP, while each database is service-owned. That limits direct coupling but means cross-service updates are not one ACID transaction.”

“How does difficulty adapt?”

“One structured LLM decision sees the transcript, current difficulty, question count, role and resume. It chooses the next action, question and next difficulty together so the question and difficulty decision stay aligned. The service also enforces the question limit itself.”

“What would you add for real time?”

“Bidirectional streaming, VAD/endpointing, partial ASR events, chunked TTS, cancellation/barge-in, reconnect and ordering semantics, backpressure, plus stage-level latency and quality telemetry. That is a different session architecture, not a model-name swap.”
